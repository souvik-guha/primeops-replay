PrimeOps Replay

Reconciles client trade allocations against broker executions, as of any moment in the day. Python and SQL.

Code on GitHub Changelog

My intention with this project was to understand one piece of middle-office work properly. When a broker fills a block order, the client sends instructions splitting the shares across its accounts. Those instructions get corrected, resent and sometimes arrive out of order. If the split doesn't match the fill, there's a break to fix before settlement.

The tool answers two questions: does the allocation match the fill, and what could an analyst have seen at a given time? All data is synthetic (made up for testing, with no real clients or trades).

One trade, four messages

The broker buys 10,000 Tencent (0700.HK) shares for a client.

Why it's built this way

Corrections replace

Revision 2 is the whole new split. Adding it on top of revision 1 would turn 10,000 shares into 19,500.

Duplicates count once

Systems resend messages. Counting both copies would create a false over-allocation.

Nothing is overwritten

Inputs never change, so any earlier view can be rebuilt. That's the audit trail.

Bad messages don't stop the run

A malformed message is rejected with a reason, and the trade stays on the break report until a valid one arrives.

Python and SQL

The rules run twice: in Python (engine.py) and as one SQLite query using window functions (sql/as_of.sql). Tests check that both give the same answer at every message time, on the sample data and on 300 randomly generated messy cases.

The report command writes open breaks to a CSV for Excel, with cells escaped so nothing in the file can run as a formula.

Not covered

Settlement (T+2 in Hong Kong), margin, stock borrow and custodian matching. This tells you the allocation matched, not that the trade settled.
